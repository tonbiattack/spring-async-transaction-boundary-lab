# 題材重複調査レポート: `@Async` 通知がコミット前の請求書を読む

## 調査対象

| 項目 | 内容 |
| --- | --- |
| 対象言語 | Java 21 |
| 難易度プロファイル | 実践・上級 |
| 候補題材 | Springの `@Async` ワーカーがコミット前の請求書を読めない問題 |
| 観測可能な契約 | `invoice-001` を保存して通知を開始したとき、ワーカーはコミット済み請求書を読めるべきだが、バグ状態では `invoiceVisible=false` となる。 |
| 直接原因 | スレッド束縛のトランザクションと別Executorの `@Async` ワーカーの実行時点が一致しない。 |
| カタログ更新日時 | 該当なし。`/home/ubuntu/repository-catalog/data/repositories.json` は環境内に存在しなかった。 |
| 検索語 | `@Async`, `Transactional`, `transaction`, `commit`, `thread`, `CompletableFuture`, `invoice` |

## 調査方法と制約

指定スキルの標準カタログは利用できなかったため、カタログの自動更新・語彙スコアリングによる新規性判定は実施していない。その代わり、ユーザー指定の `qiita` リポジトリ全体を、`@Transactional`、自己呼び出し、非同期、`CompletableFuture`、トランザクションの語で横断検索し、近接する記事の本文を確認した。

したがって、本レポートの「重複なし」は、利用可能だったQiita記事群と、この作業で作成したSpring自己呼び出しラボに対する手動比較の結論である。ユーザーの全リポジトリを網羅するカタログに基づく新規性主張ではない。

## 近接候補の比較

| 既存教材・記事 | 既存の原因 | 既存の実境界・最終観測 | 今回の差分 | 判定 |
| --- | --- | --- | --- | --- |
| `spring-transaction-self-invocation-lab` | 同一Beanの自己呼び出しが `@Transactional` プロキシを迂回する | 例外後にH2から残高を再読込し、ロールバックを確認する | 今回は `@Async` が別スレッドで実行される時点とコミット時点を扱う。修正は別Bean化ではなくコミット後イベントである。 | 重複なし |
| Springの`@Async`自己呼び出し記事 | 同一Bean内の `@Async` 呼び出しがプロキシを迂回し、同期実行になる | 実行スレッド名を観測する | 今回のワーカーは専用Executorで実際に非同期実行される。問題はスレッド切替後の請求書可視性である。 | 重複なし |
| `CompletableFuture`例外原因記事 | `CompletionException` による例外型のラップ | 戻り値のリトライ判定と原因例外を観測する | 今回は `CompletableFuture` の例外表現を扱わず、Spring JDBCトランザクションの可視性をH2で観測する。 | 重複なし |
| `REQUIRES_NEW`で監査ログを残す記事 | 外側トランザクションのロールバック後にも監査ログを残したい | SQLログと監査ログの最終件数を観測する | 今回は新規トランザクションを開始しない。非同期通知をコミット後に開始して、既存データを読めるようにする。 | 重複なし |

## 結論

作成する。

今回の題材は、直接原因が「自己呼び出し」「例外ラップ」「`REQUIRES_NEW`」ではなく、スレッド束縛トランザクションのコミット前に非同期ワーカーが読取りを始めることにある。公開境界は請求書作成と通知開始、観測契約はワーカーからの請求書可視性、最小修正はコミット後イベントへの移行であり、近接記事と教育上意味のある差分がある。
